# Changelog

All notable changes to teamplanner are documented here (Keep a Changelog; SemVer).

## [Unreleased]

### Added
- Initial scaffold (interactive-app) on 2026-07-31.
- App skeleton (`app/`): Nuxt 4 + Nitro with Nuxt UI v4, Pinia, VueUse, Zod; ESLint; Vitest test setup against in-memory PGlite.
- F1 (in progress): email/password registration with email verification and password reset via better-auth; dev mailer logs to console when no SMTP is configured; test-set covers signup, verification gate, verify-then-login, duplicate signup (no account overwrite), wrong password, short password, reset flow, and no-account-enumeration.
- F3 (in progress): sessions (login/logout), account page with profile (name edit, verified badge, date of birth) and role overview; `/api/me` endpoint; auth route middleware; test-set covers session retrieval, unauthenticated null, and sign-out revocation.
- F4 (in progress): Drizzle schema for club (tenant root), teams, club admins, staff assignments (pending/active per F8), single-team player registrations, parent links (pending/active per F5); role helper `getUserRoles` + guards; test-set covers no-roles, admin, player+multi-team staff on one identity, parent links, unique constraints, and pending-until-verified staff.
- Database layer: PGlite embedded (dev/tests) or PostgreSQL via `DATABASE_URL` (prod), Drizzle migrations applied at server startup.
- Pages: landing, register, login (with conditional Google button for F2), forgot/reset password, account (Dutch UI).
- F6 (in progress): club bootstrap - the first authenticated user creates the single club (v1) and becomes its admin; club rename by admin; `/api/clubs` + `/api/clubs/current`; test-set covers bootstrap, admin grant, rename, second-club rejection, non-admin rejection, slug validation.
- F7 (in progress): team management - admin-only create/rename/archive with archived teams excluded from the default list; `/api/teams`; test-set covers CRUD, non-admin 403s, name validation, 404s.
- F8 (in progress): member administration - admin assigns registered players by email (one team per player, DB-enforced), staff added by admin become active immediately while staff added by active team staff are pending until admin verification, admin verify/reject/remove, member lists visible to team members and managers, email lookup for admin/staff; `/api/teams/:id/members|players|staff`, `/api/staff/:id[/verify]`, `/api/users/lookup`; test-set covers all main flows plus 12 permission/constraint edge cases.
- Admin UI (Dutch): `/admin` with club bootstrap form, club settings, team list/create/archive; `/admin/teams/:id` with player and staff management incl. pending-approval flow; "Beheer" header link for admins/staff.
- F5 (in progress): parent-player linking + age-based attendance management - linking works in both directions (player enters parent email or vice versa) with confirmation by the other party via an emailed token link (`/confirm-parent-link`); age rules as pure functions (`age-rules.ts`): self-manage at 15+, under-15 via per-account checkmark set by a linked parent or admin, parents manage until 18, at 18+ the player owns the opt-in "mijn ouder mag mijn aanwezigheid beheren"; `canManageAttendanceFor` helper ready for F13; date of birth now enforced at player registration; account page grew link management, per-child settings and DOB editing; login honors a `redirect` query (mail links survive the login hop); `/api/parent-links` CRUD + confirm, attendance-settings endpoints; test-set covers age boundaries (15th/18th birthday), both link directions, token/permission edge cases and settings authorization (23 tests).
- `docs/FEATURES.md` - feature backlog F1-F19 logged ahead of build (identity and access, club and teams, trainings and schedule, attendance, communication, platform) plus architecture principles and stack decisions.

- F10 (in progress): trainings - weekly slots per team (season-bound) that materialize sessions on creation, skipping no-training periods; reusable club locations register; seasons; trainer per session (must be active team staff); one-off sessions; edit/cancel with mandatory visible reason and reinstate; **two-level no-training periods**: club-level closures (admin) cancel sessions across all teams and block new/reinstated sessions on those dates - a team can never supersede admin boundaries - and team-level periods (staff) for the team's own schedule; pure date logic in `schedule-dates.ts`; admin UI grew locations/seasons/closures cards and the team page grew slots, upcoming schedule with cancel/reinstate, one-off form and team periods; `/api/locations|seasons|no-training-periods|slots|sessions` + team-scoped routes; test-set covers weekday/season-bound generation, closure boundary inclusivity, permission matrix, cancel cascades in both scopes, 409s on closure dates, slot edit regeneration and slot deletion history preservation (24 tests).

- F11 (in progress): upcoming schedule view - `/schedule` shows every team the member is involved with (player / staff on all their teams / parent of a player), with combined role badges, upcoming sessions oldest-first, "vandaag" marker and cancelled sessions visible with reason; "Schema" header link for all signed-in users; `GET /api/me/schedule`; planned-absence visibility follows when F13 builds the absence machinery; test-set covers all role paths, combined roles without duplicates, cancelled visibility, empty schedule and horizon bounds (7 tests).

- F12 + F21 (in progress): matches on the same schedule/absence machinery - `type` column on sessions with opponent, home/away, free-text location (away grounds stay out of the club register) and external UID; manual match creation (end time defaults to start + 2h); **matches are exempt from no-training periods** (league-scheduled): closures cancel only trainings and never block or cancel matches. Sportlink `.ical` import with **preview before load**: dependency-free RFC 5545 parser (folded lines, TZID/UTC datetimes, escaping), opponent + thuis/uit derived from the summary (home side first), all-day rows skipped with reason, re-import safe via UID dedupe plus date+time+opponent fallback; team page grew a Wedstrijden card (file -> preview with checkboxes -> import, plus manual form) and the Programma/schedule views show match badges; test-set covers parser edge cases, preview idempotence, dedupe both ways, permission matrix and the closure-exemption rules (12 tests).

- F13 + F15 (in progress): opt-out absence tracking + transparent attendance stats - absence rows are the active notification, classified at report time (`>= 1.5 h` before start = timely, under that = late, at/after start = no-show); reporting allowed for the player themself or a linked parent per the F5 age rules; withdraw before start (staff/admin anytime); staff corrections: record no-shows after the session, remove incorrect absences; absences visible on every schedule surface (F11 note closed): member schedule shows "Afgemeld: ..." per session with an afmelden/intrekken flow driven by server-computed `manageablePlayers`, team page shows them with staff controls; roster (incl. parents, who now also see `listTeamMembers`) gets the Aanwezigheid card: per-player percentage over past scheduled trainings (matches and cancelled sessions excluded) with timely/late/no-show counts, color-coded; `/api/sessions/:id/absences|no-shows`, `/api/absences/:id`, `/api/teams/:id/attendance-stats`; test-set covers classification boundaries (90 min, at-start), the full F5 permission matrix, duplicate/cancelled-session/foreign-player rejections, withdraw windows, staff no-show timing, transparency payloads and stats math incl. exclusions (17 tests).

- F20 (in progress): club branding & theming - admin uploads the club logo (PNG/JPEG/SVG/WebP, max 1 MB, stored on the club record, served via `/api/clubs/:id/logo` with the byte payload never leaking into JSON); the theme primary color is **derived from the logo** client-side at upload (pure pixel-bucketing that skips white/black/grey/transparent) as the default and stays configurable via a color picker; the color applies app-wide through the `--ui-primary` CSS variable and the header shows logo + club name; `PATCH /api/clubs/:id/branding`; test-set covers the color-derivation edge cases, upload permission/mime/size limits, logo round-trip, hex validation and clearing (6 tests).

- F22 (in progress): default admin account - a fresh install (zero users) seeds `admin@teamplanner.local` with an **empty password** and `mustSetPassword`; the login page detects the pending first-run state and routes to `/setup-admin`, where the real password is set (one-shot: 410 forever after) and all empty-password sessions are revoked; while `mustSetPassword` is set the server blocks every API except `/api/me` + `/api/me/password` and a global middleware funnels to `/change-password`; the bootstrap admin administers the club without a `club_admins` row; existing databases are never touched by the seed; test-set covers seeding (fresh/idempotent/existing-install), the gated empty-password state, policy-checked first-run set, session revocation, one-shot 410 and admin rights (10 tests).
- F23 (in progress): admin creates accounts directly - Beheer card "Account aanmaken" creates a member account without self-registration or verification mail (**unverified email addresses allowed**; the admin vouches, `emailVerified` is set so sign-in works immediately); admin sets name, email, optional date of birth and an initial policy-checked password, with "must change password on first login" on by default (same `mustSetPassword` gate as F22); `POST /api/users`, own-password change at `POST /api/me/password` (better-auth verified, revokes other sessions, clears the gate); test-set covers the main flow incl. no-mail and immediate sign-in, club-first 409, non-admin 403, duplicate 409, weak initial password 400, the full gate matrix and both change-password edges (10 tests).
- F24 (in progress): enforced password strength policy - pure rule-based scorer (`password-strength.ts`, shared client/server): length + character-class points, common-password and repeated-char blocks, levels weak/medium/strong; **standard is medium-or-higher**, enforced server-side on every password-setting path (signup, reset, change, first-run, admin-create) via a better-auth before-hook plus the service checks; club setting `passwordPolicy` (low/medium/strong) editable in Beheer with an **are-you-sure dialog (yes/cancel) before lowering below the standard**; live strength labels on all password forms; `PATCH /api/clubs/:id/password-policy`; test-set covers the scorer rubric, per-path enforcement incl. reset tokens, policy ordering, non-admin 403 and behaviour after lowering/raising (20 tests).

- F25 (in progress): Beheer restructure - admin screens organized into main categories with a **navigation bar on the right** (Club, Thema, Gebruikers, Teams, Locaties, Schema, Systeem) as section pages under `/admin/*` instead of one long card list; Systeem is visible to instance admins only; the team detail page now renders inside the same shell.
- F26 (in progress): **instance admin separate from club admin** - the deployment is not the club (one instance can hold multiple clubs later, no-regret now): new `instance_admins` role and `instance_settings` (date format, time format, week numbering; lazily created defaults) with Systeem UI to edit settings and grant/revoke instance admins (never the last one); creating a club is now instance-admin-only (creator still becomes its club admin); account creation (F23) allowed for instance admins (even before a club exists) and club admins; the F22 bootstrap admin is the first instance admin and **no longer implicitly club admin**; pre-split databases are backfilled once at boot (bootstrap admin promoted); date/time formats apply through a shared `useFormats` composable in the schedule views; test-set covers settings defaults/update/permissions, the separation both ways, grant/revoke incl. last-admin protection and the backfill (13 + 2 tests, plus updated F6/F22/F23 sets).
- F27 (in progress): **club locations** - locations can be marked as club locations (checkmark) and exactly one is the club's **main location** (its own address/main site): `clubs.main_location_id` + `locations.is_club_location`, `PATCH /api/clubs/:id/main-location`, setting main auto-marks club location, the main location cannot lose its mark (choose another first), deleting it clears the pointer; Locaties UI grew the checkmarks and main-location controls; test-set covers the single-main invariant, auto-marking, clearing, permissions and deletion (9 tests).

- F24 (in progress, round 2): policy descriptions shown next to the select (each level explains its enforcement rules) and a new **'Aangepast' (custom) option**: admin defines minimum length (8-128) and which character elements are required (kleine letter, hoofdletter, cijfer, leesteken); custom rules stored on the club, enforced through the same shared evaluator on every password path; common passwords stay blocked under every policy; the are-you-sure dialog now also fires for custom rules that are **weaker than the medium standard** (heuristic: the weakest rule-compliant password is scored); test-set grew custom-rule matrix, the weaker-than-medium heuristic and end-to-end custom enforcement at signup (10 new tests).
- F25 (in progress, round 2): **navigation bar placement is a theme setting** - left (new default), top bar, or right; stored on the club (`nav_placement`), editable under Thema, applied by the Beheer shell (7 new tests incl. branding isolation).

- F28 (in progress): **KNVB speeldagenkalenders** - instance-level fetch function (Systeem) downloads the six official 2026/'27 kalender PDFs from knvb.nl and parses them via positioned-text column-band reconstruction (`knvb-kalender.ts`, pure + offline-testable; tolerates source typos like `au.g`); stored as kalenders/columns/days/cells with **pending -> activate lifecycle**: after activation a fetch produces a **diff** (day/column/cell/date/remark granularity) presented for review with **export to .md**, then *verwerk wijzigingen* (applies + logs each exact change to the **central changelog**, visible to all clubs and staff under Beheer > Schema, and remaps team selections by column title) or *annuleer* (active stays untouched); separate **force reload** behind a warning dialog dumps and renews the whole model; selection model: club sets its **KNVB-regio** + "landelijk spelende teams aanwezig" flag (Club), each team picks its **category** = a kalender column (team page), validated server-side against region/national; the six real PDFs are committed as test fixtures and the test-set **verifies DB dates against hand-transcribed PDF dates**, the full lifecycle incl. diff/process/cancel, changelog exactness, remapping, force reload and permissions (32 tests).

- F9 (in progress): **email invitations** - invite an unregistered email to register and land in the right team/role: club-scoped invitation tokens (14 days valid, parent-link pattern, token only ever travels in the mail) for **player** (admin-only, mirrors F8) or **staff** (admin invite -> active on accept; active team staff invite -> pending until admin verifies, F8 semantics snapshotted at invite time); registered emails are refused (409) - the existing F8 assignment flows cover them, and a stale expired invite is superseded by a new one; the mailed link lands on **/accept-invite**: a new user registers in place (email fixed by the invitation, F24 policy enforced, account email-verified by the token per the F23 reasoning, auto sign-in after), a logged-in user with the matching email accepts directly, mismatches get a clear message and existing accounts are routed via login (redirect back); team page grew 'Uitnodigen' next to 'Toevoegen' (Spelers admin-only, Staf admin/staff) plus an "Openstaande uitnodigingen" card with intrekken, and Beheer > Gebruikers lists all pending club invitations; cancel allowed for admin or the inviter; `POST/GET /api/invitations`, `DELETE /api/invitations/:id`, public `GET /api/invitations/lookup` + `POST /api/invitations/accept`; test-set covers both accept variants, both staff paths, listing scopes, cancel, and 15 edge cases (expiry 410, double accept, policy, DOB requirement, wrong-account 403, meanwhile-registered 409, already-player 409, permission matrix) (23 tests).

- F18 (in progress): **production deploy stack** - `deploy/` per the WhereLog pattern: `compose.yaml` with `tp-app` (Nuxt/Nitro full-stack) + `tp-db` (Postgres 17-alpine; no host port, named `tp-pgdata` volume as the single backup surface since all app state incl. logo uploads lives in the DB), app waits for the db healthcheck and gets `DATABASE_URL` assembled from the `POSTGRES_*` vars (password required, no default), commented Traefik label block ready for the proxy hosts; multistage `deploy/app/Dockerfile` (node:22-alpine, `npm ci` + `nuxt build`, runtime ships `.output` **plus the Drizzle migrations at the path the startup migration plugin resolves**, non-root uid 10001, `HEALTHCHECK` on `/api/healthz`); `deploy/.env.example` (better-auth, Gmail-SMTP MVP mail settings per docs/research-email-delivery.md, Google OAuth) + root `.dockerignore` (keeps host `node_modules`/`.data`/`deploy/.env` out of the build context); `deploy/README.md` with run/backup notes - `docs/deploy-to-<host>.md` still follows at first real deploy (host TBD); compose validated with `docker compose config`; test-set guards the config contracts: service topology, db-not-exposed, healthcheck gating, volume persistence, migrations path vs `server/utils/db.ts` resolution, non-root/healthz/EXPOSE-vs-ports coherence, env completeness both ways (compose interpolations and prod-relevant app vars, dev-only vars excluded) and `.dockerignore` coverage (16 tests).

- Research notes (docs, no runtime change): `docs/research-email-delivery.md` - production mail routing, provider comparison with verified 2026 pricing, mailbox-provider requirements under 5k/day, and the **decision** to send MVP mail via a plain Gmail account with a domain-registered sender at hosting time; `docs/research-knvb-url-discovery.md` - three seasons of evidence that KNVB asset IDs and slugs are unpredictable while the landing page is stable, the basis for the F28 URL-discovery build; `docs/research-club-teams-source.md` - **no free, club-independent automated source exists for a club's full team list**: Sportlink Club.Dataservice is paid and club-controlled, voetbal.nl is rejected on its gebruikersvoorwaarden (account-for-others, sharing and scripted *and* manual scraping all forbidden; termination without notice puts users' KNVB accounts at risk), public aggregators carry first teams only - recommendation is a convention-based team picker (JO/MO/senior/VR/35+/45+/zaal names generated from KNVB conventions) plus the always-available manual add.
